# 2026-07-01

## Redis connection `options` pass-through

- **Intent:** The Redis config block (`config/database.py`/`package.py` `redis.connections.*`) had
  no way to pass arbitrary client tuning into the underlying `redis.asyncio` client, unlike a
  database connection which already accepts an `options` dict (→ SQLAlchemy `connect_args`). Give
  Redis the same escape hatch.
- **Changed:** `uvicore/redis/redis.py` `connect()` now reads an optional per-connection `options`
  dict and splats it into `redis.from_url(conn.url, **options)`. Mirrors `database/db.py:130`
  (`connect_args = dict(connection.options) if connection.options else {}`). A missing `options`
  key auto-vivifies to an empty (falsy) `Dict` on the SuperDict, so connections without it pass no
  extra kwargs and behave exactly as before. Purely additive, no breaking change.
- **Config:** added an `options: {'health_check_interval': 30}` example to the app1 test config's
  `app1` redis connection (`tests/apps/app1/config/database.py`) so it's exercised end-to-end, and
  a commented example to the schematic stub (`schematic/acme/appstub/config/database.py`).
- **Tests:** `tests/test_redis/test_redis.py` — new `test_redis_connection_carries_options` (no
  server needed; asserts the `options` dict survives config-merge + `init()` and that a connection
  without options is falsy). `tests/integration/test_redis_service.py` — new
  `test_connection_options_pass_through_to_client` asserting the value reaches the live pool
  (`client.connection_pool.connection_kwargs['health_check_interval'] == 30`, `cache` default 0).
  Full unit suite green (531 passed); integration options test verified green against a real redis.
- **Docs:** `docs/deeper/redis.md` (Configuration section + example), `epologue/changelog/0.4.md`
  (new 0.4.5 section), `epologue/release-notes.md` bullet. `mkdocs build --strict` exit 0.
- **Version:** bumped 0.4.4 → 0.4.5 (`pyproject.toml` + `uvicore/__init__.py`); 0.4.4 was already
  released so this ships as 0.4.5.
- **Note:** engines are still cached per connection URL. Two distinct connection names with an
  identical URL but different `options` would share the first-created pool — a pre-existing dedup
  behavior, unchanged here and not a concern for the normal (distinct-URL) case.
