# 2026-08-27

## Configurable engine pooling + Snowflake connections that survive past 4 hours (0.4.11)

- **Intent:** A fleet of infinite-loop Snowflake stream consumers (vfi-loader-snowflake-uvicore-app)
  failed every query ~4h after boot with `390114 (08001): Authentication token has expired`, and
  stayed broken until each process was killed and restarted. Root-caused to the framework, so fixed
  here rather than papered over per-app. The same investigation showed `pool_pre_ping=True` was
  hardcoded in `Db.init()` with no way for an app to change it — and applied to the **sync** branch
  only, leaving async engines (the majority) with no stale-connection protection at all.

- **Changed:** Three things, all read out of the installed
  `snowflake-connector-python==4.7.0` / `snowflake-sqlalchemy==1.10.2` / SQLAlchemy 2.x source
  rather than guessed. See `adr/0009-*` for the full reasoning and the rejected alternatives.

  **1. Per-connection `pool` config block.** Unprefixed keys (`pre_ping`, `recycle`, `size`,
  `max_overflow`, `timeout`, `use_lifo`, `reset_on_return`) → `create_engine()`'s `pool_*` kwargs
  via the new `Db.POOL_OPTIONS` map, resolved by the new **pure** `Db.engine_pool_kwargs()` so
  pooling is unit-testable per dialect without a live database (same pattern as
  `configure_connection()`). Unknown keys **raise**: a silently-dropped `pool_recycle` (the
  prefixed spelling, the obvious mistake) would look configured and do nothing, which is the exact
  class of bug the block exists to prevent. Only `pre_ping` is defaulted — `size`/`max_overflow`
  are rejected outright by SQLAlchemy's StaticPool/NullPool, which is what a sqlite `':memory:'`
  url gets, so a framework default would break the simplest connection there is.

  Applied identically to sync AND async now. That means **async engines gain pre-ping**, the one
  user-observable behavior change in this release; opt out per connection.

  **2. Snowflake keeps its session alive by default.** `configure_connection()` now `.defaults()`
  the snowflake connect options to `client_session_keep_alive: True` +
  `client_session_keep_alive_heartbeat_frequency: 900`. The connector renews the ~1h session token
  (`390112` → `_renew_session()`) but on `390114` MASTER_TOKEN_EXPIRED it only sets
  `connection.expired = True` — and nothing in the connector ever reads that flag; key-pair auth
  has no re-auth path either. So the ~4h master token was simply allowed to age out. 900s rather
  than the connector's 3600s default because the connector clamps to
  `[master_validity/16, master_validity/4]` = `[900, 3600]` regardless, and a heartbeat is a
  token-only REST call (no query, no warehouse credits) so the cheap end buys 4 renewal chances per
  window instead of 1. `.defaults()` so app config always wins.

  **3. New `uvicore/database/snowflake.py` — terminal token codes are DISCONNECTS.** This is the
  part that turned a 4h hiccup into a wedged process: `snowflake-sqlalchemy` declares no
  `is_disconnect()`, so SQLAlchemy treated the expired token as an ordinary `ProgrammingError`,
  rolled the connection back and **returned it to the pool**, then handed it back out forever.
  `pool_pre_ping` cannot rescue that — its `SELECT 1` raises the same ordinary error and
  `pool/base.py` invalidates only on a `DisconnectionError`. Now a `handle_error` listener flips
  `ctx.is_disconnect = True` for 390110/390113/390114/390115, which makes SQLAlchemy invalidate the
  connection *and* `_invalidate()` the pool. `390112` deliberately excluded (the connector heals it
  itself). Attached **per engine** (not to the `Engine` class) and armed by `Db.init()`, so a
  Postgres sibling pays nothing and an engine rebuilt by a re-init/warehouse-switch is re-armed.
